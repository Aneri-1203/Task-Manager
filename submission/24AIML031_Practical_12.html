Practical 12: CI/CD Pipeline with GitHub Actions

Practical Statement

  • Implement a Continuous Integration (CI) pipeline using GitHub Actions for the Task Manager application.
  • The pipeline must automatically run on every push and pull request to the main branch.
  • It must install dependencies, run automated tests, and verify the production build.
  • Demonstrate a deliberate pipeline failure followed by a successful green run.
  • All tests must be meaningful and test actual application functionality.

1. GitHub Actions Workflow Configuration

The CI pipeline is defined in .github/workflows/ci.yml. It runs two parallel jobs: backend tests and frontend build verification.

Workflow File: .github/workflows/ci.yml

name: CI Pipeline

on:
  push:
    branches:
      - main
      - master
  pull_request:
    branches:
      - main
      - master

jobs:
  test-backend:
    name: Backend Tests
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository code
        uses: actions/checkout@v4
      - name: Set up Node.js runtime (v20.x LTS)
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'
          cache: 'npm'
      - name: Install backend dependencies
        run: npm install
      - name: Execute automated Jest & Supertest API tests
        env:
          NODE_ENV: test
          JWT_SECRET: ci_test_jwt_secret_key_98765
        run: npm test

  build-frontend:
    name: Frontend Build Check
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository code
        uses: actions/checkout@v4
      - name: Set up Node.js runtime (v20.x LTS)
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'
          cache: 'npm'
          cache-dependency-path: client/package-lock.json
      - name: Install client dependencies
        working-directory: client
        run: npm install
      - name: Verify React/Vite production build
        working-directory: client
        run: npm run build

Step 1 — Introduce deliberate failure

Key Questions

1. What is Continuous Integration (CI) and why is it important?

Continuous Integration (CI) is the practice of automatically building and testing code every time a developer pushes changes to a shared repository. It is important because it catches bugs early, ensures code quality, and prevents integration problems by validating every change against the full test suite before it reaches the main branch. In this project, GitHub Actions automatically runs all 22 API integration tests on every push to main, ensuring no broken code is merged.

2. What is the difference between CI (Continuous Integration) and CD (Continuous Deployment)?

CI automatically tests and validates code on every commit. CD (Continuous Deployment or Continuous Delivery) goes further by automatically deploying validated code to a staging or production environment. In this project, the pipeline implements CI — it tests and builds the application but does not automatically deploy it. Adding a deployment step (e.g., to a cloud service like Render or Railway) after the build step would complete the CD pipeline.

3. Why must the automated tests pass before the CI pipeline is considered successful?

The entire purpose of CI is to guarantee that every change maintains the application in a working state. If tests fail, it means the committed code has broken something. GitHub Actions exits with a nonzero status code when tests fail, marking the workflow run as failed. This prevents broken code from being merged and alerts the developer immediately. In this project, the deliberate failure demonstration shows exactly this — the wrong assertion caused the pipeline to fail, and fixing it restored the green status.
